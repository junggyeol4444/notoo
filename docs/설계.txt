AI Novel Factory — 설계 문서
================================================================================
기획안 57개 항목 중 Phase 1(참고작 분석)과 Phase 2(장기기억 DB)의 구현 설계.


1. 왜 이 구조인가
--------------------------------------------------------------------------------
250화짜리 장편을 쓰려면 작품의 모든 설정을 매 회차 프롬프트에 넣어야 하는데,
그건 불가능하다. 그래서 두 가지를 분리했다.

  (1) 작품의 사실을 검색 가능한 레코드로 쪼갠다      → Phase 2 (장기기억 DB)
  (2) 참고작에서 배울 것은 '원문'이 아니라 '구조'다  → Phase 1 (분석기)

이 둘이 갖춰지면 집필은 "이번 화에 필요한 레코드만 뽑아서 프롬프트를 만든다"는
조립 문제가 된다. 그 조립기가 memory/context_builder.py다.


2. 데이터 흐름
--------------------------------------------------------------------------------
[참고작 파일]
     ↓ reference/importer      저장 + 본문 추출 (분석과 분리. 큐로 넘기기 위해)
     ↓ reference/parser        TXT/MD/EPUB/DOCX/PDF → 평문
     ↓ reference/structure     회차 분리 + 회차 내부 구간 비율
     ↓ reference/analyzer      회차별 지표 1회 추출 → 8종 분석기
     ↓ reference/profile       Reference Profile (구조 수치 + 해시 지문)
     ↓ reference/pattern       다중 작품 집계 → Genre Profile → 패턴 지시문
                                                              ↓
[새 작품]                                                     ↓
  Novel Bible ─────────────────────────────────────────────→ ↓
  Character / Knowledge / Relationship / World / Timeline     ↓
  Foreshadowing / Style Bible                                 ↓
     ↓                                                        ↓
     └──────→ memory/context_builder ←────────────────────────┘
                     ↓
              Writer Context  (Phase 3에서 LLM에 전달)


3. 참고작에서 무엇을 가져오고 무엇을 안 가져오는가
--------------------------------------------------------------------------------
가져온다 (수치와 구조):
  평균 회차 길이, 평균 문장/문단 길이
  대사·서술·속마음 비율
  회차 내부 구간 비율 (도입/전개/갈등/보상/반전/클리프행어)
  사건 발생 주기, 대형 사건 간격, 첫 사건 위치
  클리프행어 사용률과 8종 유형 분포
  복선 설치-회수 간격 분포
  감정곡선의 변동성과 6단계 분포
  인물 수, 등장 간격, 대사 점유율, 퇴장 방식
  관계 상태 전환 간격

가져오지 않는다:
  원문 문장 (해시 지문만 남긴다. 해시에서 원문 복원 불가)
  등장인물 이름
  고유명사, 지명, 조직명
  세계관 설정
  줄거리

Reference Profile을 DB에 넣을 때 as_dict()는 기본적으로 이름을 담지 않는다.
include_names=True는 관리 화면에서 눈으로 확인할 때만 쓴다.


4. 우선순위 규칙
--------------------------------------------------------------------------------
Novel Bible > Reference Profile

작품 고유 설정이 항상 이긴다. 이 규칙을 코드 세 곳에서 강제한다.

  - context_builder.to_prompt()가 Novel Bible을 맨 위, 참고 패턴을 맨 아래에
    배치하고, 충돌 시 Novel Bible을 따르라고 프롬프트에 명시한다.
  - Reference Pattern은 단일 값이 아니라 범위(target_band)로 나온다.
    참고작 평균을 정확히 맞추는 것은 모방이다.
  - 참고 강도 0을 주면 그 항목은 집계에서 완전히 빠진다.


5. 한국어 처리에서 내린 결정
--------------------------------------------------------------------------------
형태소 분석기(konlpy/mecab)를 쓰지 않는다.
  설치 부담이 크고, 여기서 필요한 것은 "어절에서 조사를 떼기" 하나뿐이다.
  대신 정확도 한계를 문서화하고, 개별 판정이 아니라 집계값만 신뢰한다.

사전 매칭은 어절 경계를 지킨다.
  단순 부분문자열 검색을 쓰면 "커피"의 "피"가 부정어로, "실적"의 "적"이
  적대 표현으로, "서울"의 "울"이 울음으로 잡힌다. 2음절 이하 사전 항목은
  어절 시작 위치에서만 인정한다. 3음절 이상은 우연한 포함이 드물어 자유 매칭.

서술어 어미 검사는 어절이 아니라 어간에만 건다.
  어절에 걸면 조사 자체가 서술어 어미로 끝나는 경우가 막힌다.
  실제로 에게 / 에서 / 께서 / 라고 / 까지 / 보다 / 에게서 / 한테서 / 이라고가
  각각 게·서·고·지·다로 끝나서 전부 차단됐던 버그가 있었다.

인명 추출은 빈도가 아니라 '사람에게만 나타나는 신호'로 판정한다.
  빈도만 쓰면 "회사는"이 "도윤은"만큼 자주 나와 구분이 안 된다.
  호격/존칭 조사, 발화동사 근접, 성씨로 시작하는 3음절, 주격 편중을 점수화한다.
  31화 픽스처에서 후보 161개 → 실제 인물 5명으로 수렴했다.


6. 저장소 선택
--------------------------------------------------------------------------------
SQLite가 기본. NF_DATABASE_URL 하나로 PostgreSQL로 간다.

SQLite에서 외래키 PRAGMA를 켠다. 이걸 빼면 SQLite에서는 통과하고 PostgreSQL에서만
터지는 무결성 오류가 생긴다.

벡터 검색은 인터페이스로 분리했다. 지금은 파이썬 코사인 유사도를 쓴다.
한 작품의 조각만 메모리에 올려 비교하므로 250화 * 회차당 수 개 조각이면
수천 건 수준이고, 이 규모에서는 충분하다. pgvector로 옮길 때
MemoryChunk.embedding 컬럼 타입과 search() 하나만 바꾸면 된다.


7. 트랜잭션 경계
--------------------------------------------------------------------------------
리포지토리는 커밋하지 않는다. 세션을 받고 flush만 한다.
경계는 호출하는 쪽이 정한다.

  - API: 요청 하나가 트랜잭션 하나 (app/deps.py의 get_db)
  - 스크립트: session_scope() 컨텍스트 매니저

리포지토리가 제멋대로 커밋하면 여러 테이블을 한 트랜잭션으로 묶을 수 없다.


8. 미래 정보 차단
--------------------------------------------------------------------------------
Writer에게 이번 화 이후의 정보를 주면 인물이 아직 모르는 일을 말한다.
세 곳에서 막는다.

  TimelineRepository.up_to_episode(novel_id, n)      n화까지의 사건만
  VectorIndex.search(max_episode=n)                  n화까지의 기억만
  build_context()                                    등장 전 인물, 미설치 복선,
                                                     등장 전 세계관 항목 제외

KnowledgeRepository.knows()는 기록이 없으면 '모른다'로 본다.
반대로 가정하면 인물이 알 수 없는 정보를 말하는 원고가 조용히 통과한다.

AI Novel Factory — 설계 문서
================================================================================
기획안 57개 항목 중 Phase 1(참고작 분석), Phase 2(장기기억 DB), 집필(Phase 3),
품질 검사(기획안 34~38번), 장편 기억 검색(41번), 자동 집필 스케줄러(42번)의 구현 설계.


1. 왜 이 구조인가
--------------------------------------------------------------------------------
250화짜리 장편을 쓰려면 작품의 모든 설정을 매 회차 프롬프트에 넣어야 하는데,
그건 불가능하다. 그래서 두 가지를 분리했다.

  (1) 작품의 사실을 검색 가능한 레코드로 쪼갠다      → Phase 2 (장기기억 DB)
  (2) 참고작에서 배울 것은 '원문'이 아니라 '구조'다  → Phase 1 (분석기)

이 둘이 갖춰지면 집필은 "이번 화에 필요한 레코드만 뽑아서 프롬프트를 만든다"는
조립 문제가 된다. 그 조립기가 memory/context_builder.py다.


2. 데이터 흐름
--------------------------------------------------------------------------------
[참고작 파일]
     ↓ reference/importer      저장 + 본문 추출 (분석과 분리. 큐로 넘기기 위해)
     ↓ reference/parser        TXT/MD/EPUB/DOCX/PDF → 평문
     ↓ reference/structure     회차 분리 + 회차 내부 구간 비율
     ↓ reference/analyzer      회차별 지표 1회 추출 → 8종 분석기
     ↓ reference/profile       Reference Profile (구조 수치 + 해시 지문)
     ↓ reference/pattern       다중 작품 집계 → Genre Profile → 패턴 지시문
                                                              ↓
[새 작품]                                                     ↓
  Novel Bible ─────────────────────────────────────────────→ ↓
  Character / Knowledge / Relationship / World / Timeline     ↓
  Foreshadowing / Style Bible                                 ↓
     ↓                                                        ↓
     └──────→ memory/context_builder ←────────────────────────┘
                     ↓
              Writer Context  (Phase 3에서 LLM에 전달)


3. 참고작에서 무엇을 가져오고 무엇을 안 가져오는가
--------------------------------------------------------------------------------
가져온다 (수치와 구조):
  평균 회차 길이, 평균 문장/문단 길이
  대사·서술·속마음 비율
  회차 내부 구간 비율 (도입/전개/갈등/보상/반전/클리프행어)
  사건 발생 주기, 대형 사건 간격, 첫 사건 위치
  클리프행어 사용률과 8종 유형 분포
  복선 설치-회수 간격 분포
  감정곡선의 변동성과 6단계 분포
  인물 수, 등장 간격, 대사 점유율, 퇴장 방식
  관계 상태 전환 간격

가져오지 않는다:
  원문 문장 (해시 지문만 남긴다. 해시에서 원문 복원 불가)
  등장인물 이름
  고유명사, 지명, 조직명
  세계관 설정
  줄거리

Reference Profile을 DB에 넣을 때 as_dict()는 기본적으로 이름을 담지 않는다.
include_names=True는 관리 화면에서 눈으로 확인할 때만 쓴다.


4. 우선순위 규칙
--------------------------------------------------------------------------------
Novel Bible > Reference Profile

작품 고유 설정이 항상 이긴다. 이 규칙을 코드 세 곳에서 강제한다.

  - context_builder.to_prompt()가 Novel Bible을 맨 위, 참고 패턴을 맨 아래에
    배치하고, 충돌 시 Novel Bible을 따르라고 프롬프트에 명시한다.
  - Reference Pattern은 단일 값이 아니라 범위(target_band)로 나온다.
    참고작 평균을 정확히 맞추는 것은 모방이다.
  - 참고 강도 0을 주면 그 항목은 집계에서 완전히 빠진다.


5. 한국어 처리에서 내린 결정
--------------------------------------------------------------------------------
형태소 분석기(konlpy/mecab)를 쓰지 않는다.
  설치 부담이 크고, 여기서 필요한 것은 "어절에서 조사를 떼기" 하나뿐이다.
  대신 정확도 한계를 문서화하고, 개별 판정이 아니라 집계값만 신뢰한다.

사전 매칭은 어절 경계를 지킨다.
  단순 부분문자열 검색을 쓰면 "커피"의 "피"가 부정어로, "실적"의 "적"이
  적대 표현으로, "서울"의 "울"이 울음으로 잡힌다. 2음절 이하 사전 항목은
  어절 시작 위치에서만 인정한다. 3음절 이상은 우연한 포함이 드물어 자유 매칭.

서술어 어미 검사는 어절이 아니라 어간에만 건다.
  어절에 걸면 조사 자체가 서술어 어미로 끝나는 경우가 막힌다.
  실제로 에게 / 에서 / 께서 / 라고 / 까지 / 보다 / 에게서 / 한테서 / 이라고가
  각각 게·서·고·지·다로 끝나서 전부 차단됐던 버그가 있었다.

인명 추출은 빈도가 아니라 '사람에게만 나타나는 신호'로 판정한다.
  빈도만 쓰면 "회사는"이 "도윤은"만큼 자주 나와 구분이 안 된다.
  호격/존칭 조사, 발화동사 근접, 성씨로 시작하는 3음절, 주격 편중을 점수화한다.
  31화 픽스처에서 후보 161개 → 실제 인물 5명으로 수렴했다.


6. 저장소 선택
--------------------------------------------------------------------------------
SQLite가 기본. NF_DATABASE_URL 하나로 PostgreSQL로 간다.

SQLite에서 외래키 PRAGMA를 켠다. 이걸 빼면 SQLite에서는 통과하고 PostgreSQL에서만
터지는 무결성 오류가 생긴다.

벡터 검색은 인터페이스로 분리했다. 지금은 파이썬 코사인 유사도를 쓴다.
한 작품의 조각만 메모리에 올려 비교하므로 250화 * 회차당 수 개 조각이면
수천 건 수준이고, 이 규모에서는 충분하다. pgvector로 옮길 때
MemoryChunk.embedding 컬럼 타입과 search() 하나만 바꾸면 된다.


7. 트랜잭션 경계
--------------------------------------------------------------------------------
리포지토리는 커밋하지 않는다. 세션을 받고 flush만 한다.
경계는 호출하는 쪽이 정한다.

  - API: 요청 하나가 트랜잭션 하나 (app/deps.py의 get_db)
  - 스크립트: session_scope() 컨텍스트 매니저

리포지토리가 제멋대로 커밋하면 여러 테이블을 한 트랜잭션으로 묶을 수 없다.


8. 미래 정보 차단
--------------------------------------------------------------------------------
Writer에게 이번 화 이후의 정보를 주면 인물이 아직 모르는 일을 말한다.
세 곳에서 막는다.

  TimelineRepository.up_to_episode(novel_id, n)      n화까지의 사건만
  VectorIndex.search(max_episode=n)                  n화까지의 기억만
  build_context()                                    등장 전 인물, 미설치 복선,
                                                     등장 전 세계관 항목 제외

KnowledgeRepository.knows()는 기록이 없으면 '모른다'로 본다.
반대로 가정하면 인물이 알 수 없는 정보를 말하는 원고가 조용히 통과한다.


9. Phase 3 — 집필
--------------------------------------------------------------------------------
원칙: 수치로 정할 수 있는 것은 LLM에게 맡기지 않는다.

  코드가 정하는 것 (generation/guidance.py, arc_planner.py, scene_planner.py)
    사건 일정        대형·중형 사건 회차. 참고작 사건 간격 범위 안에서 작품
                     식별자를 시드로 흔든다. 같은 작품은 언제 다시 계산해도 같다.
    Arc 경계         이상적인 경계에서 가장 가까운 대형 사건으로 옮긴다.
                     Arc의 절정이 곧 마지막 대형 사건이 된다.
    클리프행어       누적 개수로 사용률을 맞추고(비율로 보면 1화 한 번에 100%가
                     되어 2화부터 막힌다), 목표 분포 대비 가장 모자란 유형을 고른다.
                     같은 유형 연속은 막는다.
    장면             수와 분량은 목표 분량 ÷ 장면 크기 범위. 첫 장면 도입,
                     마지막 장면 훅/마무리, 가운데는 회차 구조 비율대로.
    회수 임박 복선   회수 예정 2화 이내. 마지막 화는 남은 복선 전부.
    피할 표현        Style Bible 등록 표현 + 최근 5화의 반복 표현.

  LLM이 채우는 것
    Arc 이름·목표·갈등, 회차 제목·목적·사건·감정·보상·갈등·훅 내용,
    장면별 목적·인물·장소·비트, 본문, 기억 갱신용 사실 추출.

LLM 출력 검증
  구조화 응답은 <think>·코드펜스·앞뒤 잡담·끝 쉼표를 걷어낸 뒤 pydantic으로
  검증하고, 틀리면 무엇이 틀렸는지 알려 주며 다시 요청한다.
  내용도 검증한다. 없는 인물·복선 코드는 지우고, 지시와 다른 클리프행어 유형은
  되돌리고, 이미 있는 인물을 새로 만들지 않는다.

기억 갱신과 되돌리기
  apply_memory()는 만든 행의 id와 바꾼 행의 이전 값을 기록한다. 회차를 다시
  만들 때는 이 기록만 되돌린다. 회차 번호로 지우면 사용자가 직접 넣은 같은 회차의
  설정(1화 등장 주인공 등)까지 지워진다 — 실제로 그 버그가 있었고 테스트가 잡았다.
  뒤 회차가 이미 확정됐으면 되돌리지 않는다.

유사도 검사
  장면마다 참고작 지문과 대조하고 FAIL 장면만 다시 쓴다(기획안 38번).
  몇 번 다시 써도 FAIL이면 가장 덜 비슷한 판본을 쓰고 경고를 남긴다.


10. 품질 검사와 자동 수정 (기획안 34~38번)
--------------------------------------------------------------------------------
순서 (기획안 42번): Continuity → Logic → Similarity → Style → Hook (→ Reader)
위치: 집필 다음, 기억 갱신 앞. 기억은 고친 원고에서 뽑는다.

  검사기        방식      FAIL (자동 수정)                   WARN (사람이 볼 것)
  Continuity    규칙      사망 인물이 말함 + 계획에 없음     사망 인물 언급, 미래 인물,
                                                             나이 불일치, 시간 역행,
                                                             계획 인물 부재
  Logic         LLM       high로 지적 + 인용 확인됨          low로 지적
  Similarity    지문      장면이 참고작과 겹침               회차 전체가 경계선
  Style         규칙      Style Bible 금지 표현 그대로       피할 표현, 문장·문단 길이,
                                                             대사 비율, 시점, 분량
  Hook          규칙      훅 근거 없음 (필수 회차)           약함, 유형 다름
  Reader        LLM       없음                               지루한 구간 (인용 확인됨)

FAIL과 WARN의 경계
  FAIL은 자동으로 원고를 바꾼다. 그래서 확실한 것만 FAIL이다. 규칙으로 '아마'라고
  말할 수밖에 없는 것(사망 인물 이름이 나오지만 회상일 수 있음, 날짜가 앞서지만
  회상일 수 있음, 나이가 다르지만 작중 시간이 흘렀을 수 있음)은 전부 WARN이다.

어느 장면을 고치는가
  검사기는 문제 구절(quote)을 원고에서 뽑고, locate_scene()이 그 구절이 든 장면을
  찾는다. 그래서 집필 단계에서 장면 원문을 scenes[i]["text"]로 남긴다. 장면을 못
  찾은 FAIL(회차 전체 유사도 등)은 자동 수정 대상에서 빠지고 보고서에만 남는다.

LLM 지적을 믿지 않는다
  Logic·Reader의 인용이 원고에 없으면 버린다(공백 차이는 무시, 말줄임표로 줄인
  인용은 조각마다 확인, 4자 미만 인용은 근거로 안 친다). 정해 둔 kind가 아니어도
  버린다. 버린 개수는 metrics에 남는다.

고친 판본 고르기
  라운드마다(0차 = 원고) 원고와 결과를 남기고, (FAIL 수, WARN 수, 라운드)가 가장
  작은 것을 쓴다. 고쳐도 나아지지 않으면 원래 원고가 남는다. 규칙 검사의 오탐으로
  원고가 바뀌는 것을 이것이 막는다(오탐이면 고쳐도 FAIL 수가 그대로다).

확정 회차
  status가 final인 회차는 기억 갱신이 끝났다. 원고를 고치면 장기기억과 어긋나므로
  API의 check?fix=true는 409로 막는다. 고치려면 generate?replace=true로 다시 만든다.

비용
  Logic 검사는 재검사 때마다 다시 돈다. 기본 설정(수정 2번)에서 한 회차당 LLM 호출이
  Logic 최대 3번 + 고친 장면 수만큼 늘어난다. Reader는 페르소나마다 1번이라 기본으로
  꺼 둔다(NF_QUALITY_READER).


11. 장편 기억 검색 (기획안 41번)
--------------------------------------------------------------------------------
기획안의 다섯 층이 어디 있는가
  정확한 설정 데이터    DB 테이블 → context_builder.py (인물, 관계, 정보 제한 등)
  과거 장면 의미검색    memory_chunks → memory/retrieval.py
  과거 줄거리          회차 요약 → context_builder.py (최근 5화)
  원문 확인            검색 결과가 원고 발췌다. GET /novels/{slug}/memory/search
  참고 작품 분석 정보   reference_patterns → context_builder.py

색인
  기억 갱신이 끝난(final) 회차의 장면 원문을 문단 경계로 약 800자씩 나눠
  memory_chunks에 넣는다. 조각마다 어느 임베딩 모델로 만든 벡터인지 적는다.
  모델마다 차원이 달라 섞어 비교할 수 없기 때문이다. 회차를 다시 만들면 그 회차
  조각을 지우고 새로 넣는다. 되돌리기(rollback)도 조각을 지운다.

검색어
  회차 계획 단계: 회수할 복선 설명 + Arc 목표·갈등
  장면 설계·집필·Logic 검사·자동 수정: 회차 계획의 목적·사건·갈등·보상·훅 내용
  인물 이름은 넣지 않는다. 주인공 이름은 거의 모든 장면에 나와서 검색을 흐린다.

방식 선택 (NF_MEMORY_SEARCH=auto)
  임베딩 모델이 설정돼 있고 그 모델로 만든 조각이 있으면 의미 검색. 아니면 어휘
  검색(음절 2-gram BM25). 임베딩 호출이 실패해도 어휘 검색으로 넘어간다. 집필이
  검색 때문에 멈추면 안 된다. embedding으로 고정하면 어휘 검색으로 넘어가지 않는다.

발췌
  조각 앞부분을 자르면 정작 관련된 문장이 잘려 나간다(테스트가 잡았다). 질의 어휘가
  가장 많이 든 문단을 가운데 두고 앞뒤 문단을 한도까지 붙인다.

예산
  컨텍스트가 넘치면 과거 장면 발췌를 가장 먼저 줄인다(1개는 남긴다). 설정 데이터와
  달리 빠져도 모순이 생기지는 않기 때문이다.


12. 자동 집필 스케줄러 (기획안 42번)
--------------------------------------------------------------------------------
어디서 도는가
  API 서버 프로세스 안의 스레드 하나. 최대 60초씩 나눠 기다리다 NF_SCHEDULER_TIME이
  되면 자동 집필이 켜진 작품을 차례로 쓴다. 서버 없이 돌리려면 CLI run-schedule.

작품별 설정은 novels.extra["schedule"]
  enabled, episodes_per_run, paused, pause_reason, 최근 실행 기록 20개.
  새 테이블을 만들지 않았다. 작품 하나에 딸린 작은 설정이라서다.

멈춤과 재시도의 구분
  멈춤(사람이 resume해야 다시 씀)
    - 고친 뒤에도 품질 FAIL: 그 회차는 기억 갱신 없이 held로 둔다. 틀린 원고의
      사실이 장기기억에 들어가면 뒤 회차 전부로 퍼진다.
    - 목표 회차 도달.
  다음 실행에 재시도(멈추지 않음)
    - LLM 서버 연결 불가, 생성 중 예외. 회차 단위 트랜잭션이라 그 회차는 롤백된다.
  held 회차가 남아 있으면 resume을 거부한다. 풀어 주면 다음 실행이 그 회차를
  덮어쓸 수 있기 때문이다.

중복 실행 막기
  - 같은 프로세스: 작품별 실행 중 표시(_running)와 실행 잠금.
  - 여러 워커: 예약 실행 날짜(last_scheduled_date)를 쓰기 전에 커밋한다. 경합을
    완전히 막지는 못하므로 워커 하나로 띄울 것을 문서에 적었다.
